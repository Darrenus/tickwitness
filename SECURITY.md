# Security policy

TickWitness `v0.1.0a1` is a published GitHub technical preview; no PyPI package was published. It supports the bounded trusted-owner evidence workflow described in the [release record](docs/releases/0.1.0a1.md) and [support matrix](docs/support.md). The subsequent `0.2.0.dev0` branch is unreleased development, including read-only scenario checks and a separate budgeted coupled-clock stress execution path. Neither is a calibrated independent feed-delay model. Preview availability does not provide production or hosted-service support.

Execution support follows the frozen [execution trust and threat model](docs/contracts/execution-trust-v1.md) and the versioned support matrix. Its three modes are documentation labels, not CLI/SDK flags:

| Mode | Current status and boundary |
| --- | --- |
| M0 TRUSTED_LOCAL | Supported only for existing qualified built-in profiles and authorized data. The owner, configured roots and ancestors, interpreter, dependencies and host remain trusted. A single trusted owner using SSH on a supported remote host still uses M0. |
| M1 RESTRICTED_SINGLE_HOST | Requirements only: unimplemented, unqualified and unavailable. A selected profile must establish its file/identity/environment, default-deny network, resource and stop/reclaim boundaries with actual negative evidence before enabling it. There is no silent fallback to running untrusted code as M0. |
| M2 HOSTED_UNSUPPORTED | Untrusted hosted tasks, collaboration requiring independent user/tenant permissions, and multi-tenant services are unsupported. Tenant identity/ownership/authorization, cross-user data and secret isolation, quotas and operational/security qualification require separate scope and review. |

Input and evidence IO reject unsafe paths, symlinks, special files and quota breaches within their documented API boundary; these checks do not isolate another process with owner permissions. In current development profiles, optional Job controls provide scoped CPU, single-file and FD ceilings, admission deadlines and owned-process/scratch cleanup. They do not establish memory/PID/aggregate-disk quotas, default-deny egress, a scrubbed environment or containment of hostile escaped descendants. An observed RSS or deleted-byte report is not a resource enforcement mechanism. Python subprocesses, `-I`, qualification guards, containers and hashes are not by themselves a malicious-code sandbox. Missing control evidence or unconfirmed stop remains unknown; preserve its diagnostics and scratch as required by the existing cleanup contract. Confirmation denial applies to application entry points and does not hide owner-controlled files from their owner.

Offline verification checks integrity, source bindings and the declared accounting profile. It does not authenticate an author, prove a native matching run occurred, certify real market fills, inspect confirmation observations or audit every historical trial. Arbitrary Python strategies and hosted untrusted execution are unsupported. SDK confirmation access is denied; the separate CLI [one-time confirmation access](docs/contracts/confirmation-access-v1.md) requires its own frozen authority and does not grant general unsealing, a confirmation evaluator or secrecy from the host owner. Planned controls must not be described as implemented protections.

A mode label or security test grants no research authority and does not reset the original protocol budget. Admitted failed/interrupted/uncertain attempts are not refunded; actual authorized re-execution requires a new original slot. Committed results are reverified/acknowledged rather than executed again. CI, AI review, owner acceptance, external-human reproduction and independent security review are distinct evidence; M1/M2 support cannot be inferred from any ordinary green CI run.

Do not submit secrets, private market data, proprietary strategies, or exploit details in public issues. GitHub private vulnerability reporting was enabled and verified for this repository on 2026-10-25. Use the repository Security tab to report privately. If that channel is later unavailable, open a minimal issue asking the maintainer to establish a private channel, without technical exploit details or sensitive attachments.

Preview reports are handled by the maintainer on a best-effort basis. There is no 24×7 response SLA, guaranteed response/fix deadline or announced long-term maintenance window. Acknowledge and coordinate a private disclosure before sharing sensitive details publicly; keep reproducible reports limited to the affected version, environment, error and an authorized minimal synthetic case when possible.

The preview does not promise automatic migrations. Preserve original CAS objects, catalogs, protocols, attempt ledgers and bundles before upgrading; test new versions in separate environments. Unsupported formats must be rejected without overwriting originals. For rollback, retain the previous installation artifacts and a matching complete backup. See the [upgrade and rollback policy](docs/support.md#兼容升级与回退).

See the [frozen execution trust contract](docs/contracts/execution-trust-v1.md) for current controls, residual risks and future enablement gates, and the [security and operations plan](docs/operations/security-and-operations.md) for wider rollout work. S13-01 freezes this model; it does not implement or qualify an isolated executor, hosted service or new release.
