# TickWitness 敏捷工作协议

状态：初始工作协议，2026-10-25；适用于计划阶段及后续开发。产品尚未实现，以下门禁是待执行的要求。

## 产能与责任

默认一名全职人类维护者负责产品取舍、领域确认、代码审查和发布。AI 负责辅助调研、实现、测试和文档，不能作为独立人类审批者。每 Sprint 两周，净工程预算 50h：35h 用于新增能力，15h 用于验证、评审、文档、维护与风险；估算已包含正常会议外的净工作时间，不能再把 50h 当成可写功能的时间。

单维护者不宣称实现了完整 Scrum 团队配置，采用迭代交付和持续反馈的实践。多人加入后再明确 Product Owner、领域专家、开发者及交付协调职责。量化领域专家和外部试用者的可用性是外部依赖，不是假设已具备的团队资源。

| 责任 | 初始承担方式 | 升级条件 |
| --- | --- | --- |
| 产品优先级与接受标准 | 仓库 owner | 每月用户反馈修订 |
| 领域规则与研究语义 | owner 提案，寻求量化同行复核 | 不确定规则不得静默固化 |
| 代码与设计审查 | AI 辅助 owner 检查；单人 PR 标记 self-reviewed | 有独立维护者后，高风险修改要求独立审批 |
| 发布与事故响应 | owner | 按实测支持负担增加维护人员 |
| 安全评审 | owner 建立威胁模型；开放不可信代码前寻求外部复核 | 复核不可用则限制发布范围 |

## 迭代节奏

每 Sprint 首日进行 60–90 分钟计划，选定一个可验收目标，确认上游依赖、35h 功能预算和15h质量预算。每工作日更新一次异步记录：目标进度、阻塞、下一步和已消耗预算，不以提交数评价产出。

每周一次 45 分钟 backlog refinement；第二周进行真实用户工作流 review，保留运行制品及反馈。Sprint 末进行 45 分钟回顾，最多选择两个改进行动并放入下一 Sprint。每两个 Sprint 重新细化后面两轮的任务；S9 以后的内容是条件性路线，不锁死一年的详细实现。

WIP 初期上限：一项功能 story、一项缺陷/运维任务；同一领域模块不并行改动未达成一致的语义。主干保持可验证，特性分支尽量短于三个工作日。复杂能力通过切片或默认关闭的能力开关交付，不用长期分支隔离半年。

## Definition of Ready

进入 Sprint 的 story 必须包含真实用户或维护者目标、唯一 ID、所属 bounded context、可验收结果、依赖、估算、测试数据权利和风险。涉及判定语义的 story 需列一个正例、一个反例、一个无法判断的例子；涉及状态写入的 story 需说明幂等与失败恢复。

不确定工作先 timebox spike。功能 story 建议 4–12h，硬上限16h，超过16h必须拆分；研究性 spike 每个 timebox 通常不超过6h，较大可行性故事拆成多个明确试验与整理预算，产物是证据与决策，不是承诺得到理想结果。未获得数据、专家或接口能力的依赖不能记为 ready。

## Definition of Done

1. 用户故事的验收条件在固定输入上可重复执行，失败路径和边界条件已覆盖。
2. 领域规则、应用服务、adapter 和展示层保持依赖方向；跨域修改通过契约，不直接读取别的模块内部表。
3. 新增或变更行为有与风险相称的测试。研究判定修改必须有负例和历史制品回放；文档更正不需要制造无价值代码测试。
4. CI 中实际存在的检查全部通过；尚未实现的检查不得在 README 或发布说明中写为已通过。
5. 契约、数据格式、数据库迁移、可观察性和用户文档随行为一同更新；不兼容变化有迁移和回退策略。
6. secrets、敏感策略和无权分发的数据没有进入提交或 CI 制品。
7. owner 已读过差异并接受；高风险领域/安全修改记录复核证据。没有独立人类复核时如实写明。
8. 交付的是可运行的纵向能力；未达验收条件的工作回到 backlog，不以完成百分比充当 done。

## Issue、PR 与变更控制

Epic → story → PR → 验证制品 → release note 建立双向链接。Issue 可用仓库提供的 story、defect、RFC 模板。标签建议为 `type:*`、`domain:*`、`priority:*`、`status:*`，创建标签和里程碑时从 roadmap 导入，不另建相互矛盾的真相源。

PR 描述具体触发条件、前后行为、验证方法、迁移/兼容性和局限。接口或研究语义改变先写 RFC/ADR；紧急安全修复可先合并止损，再于下一工作日补齐。只修改文档的 PR 不因模板而强制填虚构性能数据。

每 Sprint 的范围冻结以保护目标；新发现的 P0/P1 问题优先处理，同时显式移出等量功能，不能无声加班吸收。跨 Sprint 未完成任务重新估算。估算偏差超过 30% 连续两轮时，降低后续范围并检查环境、依赖和任务切片。

## 缺陷等级与支持

| 等级 | 判定 | 初始响应目标（维护者公布的支持时段内） |
| --- | --- | --- |
| P0 | 证据被静默篡改、越权执行、结论错误仍显示成功 | 当日确认；停止相关发布并提供禁用/回退办法 |
| P1 | 常见输入产生错误判定、数据损坏、无法恢复任务 | 下一工作日确认，优先下一修复批次 |
| P2 | 有替代路径的功能/兼容性问题 | 五个工作日内分类，排入常规 backlog |
| P3 | 易用性、文档、低影响边缘缺陷 | 常规 refinement 处理 |

这是初始内部服务目标，不是付费 SLA，也不承诺单人 24×7。安全漏洞按 [SECURITY](../../SECURITY.md) 处理。研究结果争议必须带输入版本、假设集合、引擎版本和复现信息，不能仅凭 Sharpe 截图定性。

## 收缩与继续投资

发布门未过先减少交易所、策略类型、引擎和 UI 范围，保留证据真实性及验证要求。四轮迭代仍无法完成可信纵向闭环时，暂停扩展和前端装饰，复查数据与引擎选择；八轮后没有用户愿意复现外部案例时优先重做用户问题验证。具体量化门槛见产品文档。

实践参考：[Scrum Guide](https://scrumguides.org/scrum-guide.html)。本协议是适合初期维护者规模的工作方式，不宣称其等同完整 Scrum 组织。
