# 产品开发路线图

状态：Proposed（拟议计划，尚未实现）。版本：2026-10-25。项目：TickWitness；目标仓库：`Darrenus/tickwitness`。当前交付是 planning baseline，0.1 技术预览须通过 S4 验收后另行发布。

本文定义交付顺序、投入假设与阶段验收门；逐 Sprint 工作见 [Sprint backlog](sprint-backlog.md)。领域边界见 [领域模型](../architecture/domain-model.md)，产品验证见 [产品与采用验证](../product/discovery-and-adoption.md)。时间与指标都是规划目标，不代表现有能力或已取得的市场结果。

## 1. 可交付的产品边界

第一版面向有现成策略与历史行情的量化研究者、研究平台维护者和研究审阅者。产品接受冻结的研究声明、观测数据、显式假设与资源预算，运行受约束的场景评估，输出结论差异、反例及可重放的证据包。

两类评估必须始终分开：

- **观测相容解释**：在已有证据没有唯一确定的范围内改变解释，例如 L2 撤单位于队列前后的位置，或带证据的时钟误差区间。
- **压力情景**：主动增加延迟、丢包或其他故障，用于回答系统对某种变化是否敏感。新增故障不能描述成实际历史已经发生的情况。

第一版围绕一个公开数据源、一个现成回放引擎和少量明确声明的策略接口做深，核心稳定范围为可安装的 CLI、Python SDK、受控搜索与作业运行、机器可读证据包、验证器、部署说明与维护政策。首版实现两种变换：额外接收延迟压力、L2 队列解释；时钟证据先记录来源与约束，取得校准证据后再扩展对应情景。

HTTP API、MCP 和报告查看器是有真实需求且通过各自验收门后才发行的可选入口，可后移或取消，不阻塞核心 GA。它们复用同一应用服务；用户无需使用 Agent 或界面，也能完成完整工作流。仓库代码许可证已选 Apache-2.0；数据、模型与第三方引擎的分发权仍分别检查。

第一版不承诺真实成交还原、全局最小反例、收益保证、自动证明策略稳健、任意历史缺包补全、任意代码的跨租户托管安全。有限预算搜索只能报告在其场景集合和预算内发现了什么。没有找到反例应返回 `NO_COUNTEREXAMPLE_FOUND` 及搜索范围，不能返回无条件“稳健”结论。

## 2. 人力、容量与节奏

基线团队为 **1 名全职维护者 + AI 辅助**。每个 Sprint 为 2 周，预留 50 小时净工程产能；其中最多 35 小时用于可计划专项（功能、研究访谈、专门验证或演练），15 小时用于日常回归、审阅、文档、依赖与维护。专项的专门验收计入该故事，公共日常工作只记账一次，二者不重复。50 小时不是要求加班，而是全职工作扣除沟通、学习和其他必要工作的有效容量假设。

24 个 Sprint 对应约 48 周。该排期表达顺序与投入上限，不是固定发布日期承诺。两至三名有经验的工程师可以并行推进数据、应用和质量工作，但仍须遵守领域契约和集成验收门，不能把排期直接除以人数。AI 不算独立审阅者，不承担发布责任，也不替代外部用户验证。

工作方式：

1. 每两周 Planning、Review、Retrospective 各一次；每天维护一个简短异步进展与阻塞记录。
2. 只把接下来两个 Sprint 的故事细化到可执行条件；更远阶段保留验收意图，按用户证据和技术试验调整。
3. 一个维护者最多同时进行一个主要功能和一个缺陷修复；未完成故事回到 backlog，不把“部分完成”计入发布能力。
4. 任何故事估计超过 16 小时，先切出可验证纵向增量；spike 按不超过 6 小时的 timebox 拆开。超过 35 小时的专项必须减 scope，不能挤占日常质量预算。可选入口没有证实需求时，用同等预算处理核心缺陷、恢复或证据验证，不额外叠量。
5. 重大正确性缺陷、不可恢复数据损坏或隔离失效优先于功能；必要时延后里程碑。
6. 每四个 Sprint 重新估计剩余投入。关键外部依赖或验证结果变化时，修订路线图并保留决策记录。

## 5. 产品成熟度的明确含义

### 0.1：可运行的基础，而非市场验证

- 用户可以在受支持环境中从空目录安装并重跑随附的合法样例。
- 只支持声明的可信本地策略接口；没有沙箱时拒绝把外部代码上传当作受支持流程。
- 样例的业务语义、原始数据许可与证据范围有说明。
- 首次 import/verify 就校验路径、symlink、大小/文件数配额并拒绝可执行反序列化；可信代码模式不豁免输入解析安全。
- 存储失败、无效序列、未知能力和数据缺口都不会被包装成成功报告。

### Alpha：核心方法能被检验

- 观测相容解释和压力情景在数据模型与输出中可区分；可选界面沿用相同语义。
- 基准包含已知分歧、无分歧对照、无效扰动和资源耗尽案例。
- 每个反例有首次分歧、具体参数、证据来源和复跑步骤。
- 搜索使用的开发/验证数据与冻结确认窗口分开；确认结果不反向用于挑选同一声明。
- 同步执行失败可见、制品原子发布；完整 job 恢复/取消到 S10 的 0.3 阶段交付，早期 alpha 不宣称已经支持。

### Beta：可由外部用户完成真实工作流

- 安装、导入、运行、取消、恢复、查看、导出、验证不依赖作者手工补救。
- 错误路径、资源限制和所声明隔离机制经过测试。
- 旧格式要么在明确支持范围内读取，要么拒绝并保留原件；最小备份恢复与关键 runbook 已实际演练。S18/S19 扩充分版本迁移与运维能力。
- 至少 3 位外部用户激活，其中至少 2 位在有限协助下完成；S12/S13 起登记激活与 30 天观察窗口。口径与 [采用计划](../product/discovery-and-adoption.md) 一致。
- 反馈进入 issue、形成可复现缺陷、经回归测试修复；用户访谈数量不能代替完成任务的证据。
- 若招募失败或没有授权可用的数据，延长 alpha，不捏造 beta 采用指标。

### 1.0：有限范围内可维护的稳定产品

- 核心 CLI、SDK、证据包格式有明确兼容政策；已发行的可选入口单独列明支持与兼容范围。
- 支持的操作系统、Python/引擎版本、数据源和信任模型形成经过验证的矩阵。
- 完成至少一次干净安装、旧版升级、备份恢复、回滚、作业中断恢复、资源耗尽和失效依赖演练。
- 无未关闭的阻塞级正确性、安全或数据损坏缺陷；重要非阻塞缺陷公开并有处理计划。
- 基准、依赖清单、产物校验、发布说明、故障处理与维护政策随版本公开。
- 至少 2 位已满 30 天观察窗口的外部用户自发用于第二个不同研究；未满足时保留候选版并继续验证，不能用维护者代跑补数。
- 1.0 表示列明范围的产品稳定性，不表示收益有效性、整个市场的认可或无限模型覆盖。

## 6. 范围控制与条件式扩展

下列工作不进入 1.0 的基线承诺：第二套自研回测引擎、通用因子工厂、真实交易执行、跨资产全覆盖、多租户公有云、GPU 世界模型、移动端、策略市场和实时排行榜。

扩展依赖具体证据：

| 扩展 | 触发条件 | 先做的最小试验 |
| --- | --- | --- |
| HTTP / MCP / 报告查看器 | 真实接入或阅读任务证明确需该入口，核心应用契约已稳定 | 仅实现受需求支持的入口，并独立测试；未获需求将原预算用于核心加固 |
| 第二个回放引擎适配器 | 独立用户确有引擎切换需求，且现有 trace 契约可表达差异 | 用同一组固定案例做语义兼容试验，不强求不同执行模型收益相等 |
| 第二个交易所 | 数据模型出现可复现的单交易所偏差，且用户愿意提供合法样例 | 只支持一个新市场的一种输入类型，验证反腐层不污染核心域 |
| PostgreSQL / 独立队列服务 | 单机目录与 SQLite 的并发或作业持续性在测量中形成瓶颈 | 复用 repository / job ports 做替代适配器，并跑同一契约测试 |
| 团队自托管 | 多名真实研究员反复共享与审阅证据，单用户流程造成阻碍 | 单组织访问控制与审计试点；不直接承诺公有多租户 |
| 托管 SaaS | 维护者有安全、值班、成本与需求验证能力 | 独立威胁建模、租户隔离和账单试验；通过前不接收不可信代码 |
| 统计稳健性模块 | 用户需要超越声明符号分歧的统计结论，且研究方法可验证 | 单独实现一个经过原始文献核对的统计检验及其试验登记，不堆砌指标 |

## 7. 主要风险与调整策略

| 风险 | 最早验证点 | 可观察信号 | 调整动作 |
| --- | --- | --- | --- |
| 引擎无法暴露必要轨迹 | S1–S3 | 无法定位首次决策/成交分歧 | 更换适配目标或缩小首个问题；不以 UI 掩盖缺失轨迹 |
| 队列模型差异只是参数扫描 | S5–S8 | 不能提供比固定 sweep 更有用的定位或复现信息 | 优先证据链与分歧定位，缩减搜索器复杂度 |
| 约束没有实测依据 | S5–S8 | 时间范围来自猜测；压力场景被误称为历史事实 | 输出“假设未校准”，限制结论；先补采证据 |
| 反例缩减破坏数据合法性 | S9 | 缩减后的流缺少必要序列或状态 | 使用有效 checkpoint；限制允许的缩减算子，放弃最小性宣称 |
| 搜索成本超过个人承受能力 | S7、S11、S20 | 大部分预算花在相同前缀回放或无效场景 | 先实现缓存/检查点与预算策略，再考虑分布式执行 |
| 不可信代码隔离不可维护 | S13 | 网络、文件、进程或资源逃逸测试失败 | 保持可信代码本地运行模式，拒绝扩展 hosted scope |
| 没有真实用户持续使用 | S8、S16、S21 | 只有观看演示，没有重复任务或可复现反馈 | 缩窄用户角色或转成引擎插件；暂停新增外围功能 |
| 数据再分发受限 | S2、每次加入数据 | 样例没有明确许可/来源 | 提供合成 fixture 和用户自行导入路径，不发布受限数据 |
| 单维护者知识集中 | 每四个 Sprint | 发布/恢复步骤只有作者能完成 | 文档驱动干净环境演练；减少依赖和运行组件 |

## 8. 持续维护与路线图更新

1.0 后仍按两周节奏维护，每月做一次依赖与支持矩阵检查，每季度重估领域边界、成本和采用证据。发布频率以质量与维护能力为准，不把每个 Sprint 等同于公开发版。

每次路线图调整记录：发生了什么、证据链接、被影响的故事、取消/后移范围、对兼容性与用户迁移的影响、下一次复核点。新增大型组件必须先证明当前结构不能满足测得需求。

当前优先级为：研究结论语义正确 → 证据可复现 → 真实用户可完成任务 → 运行可靠与维护成本可控 → 更多集成与界面能力。每个阶段都应产出可以被使用和审阅的纵向增量。
