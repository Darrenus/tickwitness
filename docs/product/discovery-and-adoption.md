# TickWitness 用户发现与采用计划

状态：执行计划，未开展访谈或试点；所有数字都是目标或门槛，不是结果。最后更新：2026-10-25。项目入口见 [README](../../README.md)，产品定位与边界见 [产品策略](product-strategy.md)。

## 1. 要验证的核心问题

在扩大开发之前，验证真实研究者是否愿意把一个已有研究交给工具审查，是否能理解工具的结论边界，以及结果是否改变下一步研究行动。第一阶段不靠问“你觉得这个想法好吗”来判断需求。

当前已知的是公开工具存在相邻能力：回放引擎已有队列和成交假设，Freqtrade 已有重复回测检测前视偏差，MCP 工具已有静态泄漏扫描。公开资料不证明用户需要另一个平台，也不证明他们愿意迁移工作流。[HftBacktest](https://hftbacktest.readthedocs.io/en/latest/order_fill.html)、[Freqtrade](https://www.freqtrade.io/en/stable/lookahead-analysis/)、[leakguard-mcp](https://github.com/doazvjettu/leakguard-mcp)

需要分别验证四件事：问题近期且真实、现有方式存在可量化缺口、产品能低成本接入、用户愿意在下一个研究中再次使用。商业意愿在这些基础上单独测试，不能用 Stars 或访谈赞同代替。

## 2. 样本选择与招募计划

S1–S2 的目标是在既定 Sprint 预算内完成 3–4 次早期痛点访谈，至 S6 累计完成 8–12 次有效问题访谈；逐步覆盖独立研究者、小团队研究工程师、评审者和引擎维护者，累计样本至少一半来自维护者既有熟人圈之外。招募、访谈、分析和案例协调均计入对应 Sprint 预算，超出时移出其他工作，不额外叠加到排期。访谈和试点均须先征得参与者同意。本计划不代表已联系任何人，也不授权自动向外发送邮件或消息。

优先条件：过去 90 天内运行过自己的回测；能描述一次执行假设或数据问题影响研究决定的案例；愿意展示现有流程的非敏感部分；已有 Python 研究代码或可接入的回放引擎。不以资金规模、已实现收益或是否公开 alpha 为参与门槛。

可选招募入口包括相关开源仓库的 Discussions、研究工程社区、个人技术文章和已有专业联系。先查看社区规则，再由维护者发出具体请求；不在他人 Issue 中发布无关推广，不要求参与者公开专有策略。

每次招募说明必须包括：项目仍在验证、需要的时间、可以提供合成或公开案例、数据留在本地的选择、哪些材料可被保存或引用，以及随时退出的方式。默认不公开参与者身份、公司、代码和行情。只保存完成该次验证必要的记录。

## 3. 问题访谈：先看行为，再看方案

建议 30–45 分钟；前半段不演示产品。可以按以下顺序开展：

1. “请带我看最近一次完成或放弃的研究，最终用什么证据作决定？”
2. “最后一次更改队列、延迟、费用或数据清洗后，结论发生了什么变化？”
3. “你怎样确定变化是策略本身、数据、引擎还是假设造成的？当时花了多少主动操作时间？”
4. “如果需要请同事复查，你交给对方什么？他能直接跑起来吗？”
5. “哪个未知量最妨碍决定？你会用哪些证据限定它，而不是随意挑参数？”
6. “你有没有因为这个问题补采数据、缩小规模、放弃研究或增加一次评审？请描述一次。”
7. 看完短演示后：“哪一步能替代你今天的工作？哪一步增加负担？你愿意用哪一个自己的案例验证？”

记录最近实际行为与受访者推测，二者分开。对“会用”“有意思”继续追问具体下个任务和可提供的投入；拒绝参与也是有效证据。研究者可能已经有足够好的脚本，应记录并纳入对照，不把现有工具熟练用户排除以获得正面反馈。

每次访谈形成一条记录，字段为：匿名参与者 ID、角色、日期、案例时间、当前工具、触发事件、现有解决法、主动操作时间、问题后果、可用证据、数据限制、反对意见、可投入的试点，以及原话/维护者解释的区分。时长或频率未经参与者确认时标记“估计”。

## 4. 试点分三步推进

### 4.1 问题验证与案例承诺

S1–S2 先用 3–4 次早期访谈检查问题方向；至 S6 的累计 8–12 次访谈中，目标是至少 5 位受访者有近期具体痛点，至少 3 位愿意提供或在本地运行自己的案例。承诺的表现是约定一次运行并准备指定输入，不是加入等候名单。

此阶段可使用手工流程展示预期报告，不假装自动化已经完成。报告明确标注哪些步骤由维护者执行。若多数人只想获取盈利信号，说明目标人群选择错误，不据此扩成交易机器人。

### 4.2 陪同试点

目标：完成 3–5 个外部真实研究案例。每个案例在运行前记录主张、约束来源、基线、预算和参与者当前处理方法。小而可以复现的案例优先于庞大但无法解释的数据集。

维护者可以帮助接入，但单独记录编写适配代码、处理输入、解释报告的时间。若案例必须依靠维护者持续定制才能运行，将它视为集成成本证据，不能算自助采用。

每个案例交付以下内容：

| 交付物 | 验收方式 |
| --- | --- |
| 固定的研究主张和允许假设 | 参与者确认它对应原研究问题，范围有数据或操作依据 |
| 基线与执行清单 | 在指定环境重放并解释数值容差，不能静默替换模型 |
| 搜索结果与覆盖说明 | 记录所有尝试及预算；有效反例必须过约束检查和独立见证重放 |
| 反例收缩或未找到说明 | 写清已检查邻域；不将经验搜索称为全局最优 |
| 研究决定记录 | 参与者选择修正、补采、继续、停止，或明确“没有改变”；保留理由 |
| 交接验证 | 由未参与原运行的人或干净环境使用产物复现 |

一个“收益从正变负”的输出不自动构成成功。反例若违反观测、依赖用户认为不合理的范围，或无法改变任何研究行动，必须记录为失败或无价值结果。

### 4.3 自助采用与复用

从可信本地 CLI/SDK 工作流可用时开始外部激活观察，最迟在 S12–S13 阶段前启动，不等待可选 API、MCP 或 UI；未支持的功能明确拒绝。Beta 的采用门是至少 3 位外部用户激活，其中至少 2 位仅依赖文档和一次有限排错帮助完成自有研究。未达采用门则保留 alpha，不能用样例完成数补足。

GA 的采用门是至少 2 位外部用户各自已满 30 天观察窗口，且在各自窗口内自发完成第二个不同研究。选择第二次任务的行为由用户自己发起，不由维护者代跑。观察未满或复用未达门槛时保留 RC，不提前结束窗口或用意向承诺替代。采用门仍须与正确性、兼容性和运维验收一并通过。

自助入口应包含：无账号安装、离线小样例、输入预检、最小适配模板、预算设置、报告阅读说明、证据包核验方法和常见失败恢复。没有准备好这些交接内容，就不广泛推广以积累大量支持负担。

## 5. 先冻结对照，再评估自动搜索

产品需要同时回答“有没有用”和“比简单脚本好在哪里”。每次实验记录数据与策略版本、约束集合、指标、预算、终止规则和算法版本；所有方法使用相同的允许范围和等价计算预算。优先比较已有手工流程、简单网格/随机扫描，以及受约束搜索。

| 实验 | 主要问题 | 需要保留的结果 |
| --- | --- | --- |
| 合成、有限且可枚举的情形 | 约束检查、结果标签和搜索实现是否正确 | 全部世界的真值、预先设计的正反对照、有效/无效见证、遗漏情况 |
| 已知缺陷的复现案例 | 能否定位一个有外部机制解释的问题 | 缺陷如何影响结果、简单基线是否同样发现、修复后变化 |
| 未见过的外部案例 | 对真实研究是否有价值 | 找到/未找到、无效候选、运行失败、解释及行动，不能只发表成功案例 |
| 盲读报告 | 用户是否理解“未发现”和“已证明”的区别 | 未经提示的判断、错误理解、导致误解的措辞 |
| 另一环境独立核验 | 产物能否交接 | 环境、版本、数值容差、失败原因及恢复步骤 |

对有限案例可以比较完整真值；真实连续搜索中的未知最坏值不能用来计算虚假的“全局召回率”。真实案例报告固定预算内的有效见证发现率与成本，并明确评估集合的来源。

对于人为新增的丢包或延迟，报告标题使用“压力情景”；对与原始观测相容的未知量，才讨论“观测不足以确定结论”。用户盲读测试中若有人把二者混淆，先修改报告与流程，再扩大宣传。

若需要统计评估方法优劣，先固定留出案例及指标，再做算法调整。不要在同一组外部案例上不断调搜索器并把结果当独立验证；训练/开发案例、回归案例和最终评估案例分开管理。

## 6. 采用漏斗与指标字典

默认不收集产品遥测。前期指标可通过参与者同意的访谈、Issue、运行摘要和试点登记手工维护。匿名化 ID 用于案例去重；自愿提交摘要前先给用户检查，任何指标采集都不是运行产品的前提。

| 阶段 | 定义 | 衡量与排除项 |
| --- | --- | --- |
| 合格触达 | 阅读或回应具体研究审查示例、且符合目标用户条件 | 普通访问量不算目标用户 |
| 样例完成 | 在本地运行官方小案例并打开报告 | CI、维护者代跑、反复安装不算独立采用 |
| 激活 | 用自己的一个研究完成基线、声明约束并获得有效完整结果 | 仅跑 demo 不算；有效完整结果可以是未发现或证据不足 |
| 价值实现 | 结果被独立复现，并形成一项参与者确认的研究决定 | 自动生成“建议”不算；决定可以是确认继续但需具体证据 |
| 复用 | 首次激活后 30 天内自发审查另一个研究 | 重跑相同样例、维护者代操作不算 |
| 团队传播 | 第二位研究者或评审者实际核验该产物 | 转发链接、Star 不算 |
| 付费验证 | 为有验收条件的试点或服务实际付款 | 口头意愿、预算猜测或无约束意向不算 |

指标看板至少包含分母、窗口、来源和缺失值。例如“2/3 位已激活且满 30 天观察窗口的外部用户复用”，不能只写“留存率 67%”。样本很小时同时展示案例明细，不做精确人口比例推断。

主要时间指标分开记录：用户主动操作时间、维护者协助时间和计算等待时间。资源指标至少包括固定数据集上的完成率、运行时、内存、磁盘和中断恢复；性能数字必须附引擎版本与硬件。

## 7. 公开发布与生态采用

项目软件已选择 [Apache-2.0](../../LICENSE) 许可；软件许可不自动覆盖第三方依赖和数据。第一份公开内容应是一项完整可复现的案例，说明原主张、观测约束、反例、对照及限制。选择公开可再分发或合成输入；若真实数据许可不明，只发布生成/下载说明、清单和合成复现，不直接上传数据。脱敏不能替代数据发布授权。

Hugging Face 可作为后续版本化案例集的候选分发渠道，而不是先建立通用行情数据仓库。发布案例集需要说明来源、许可、标签形成方式、开发与评估划分、已知局限及如何重现。真实敏感研究不进入公共排行榜，报告发现问题的数量也不能成为盈利能力排名。

对回放引擎生态，优先提供一个可独立使用的适配器和高质量 bug 复现。提交上游修复前确认问题属于引擎语义而非本项目约束实现，提供固定版本的最小案例。先建立协作可信度，再请求上游把工具列入集成目录。

社区沟通按内容分流：Issues 收集缺陷与最小复现，Discussions 收集研究问题、接入经验和未确定建议。GitHub 官方也将 Issues 定位于具体项目事项，将 Discussions 定位于较开放的交流。[GitHub 官方说明](https://docs.github.com/en/get-started/using-github/communicating-on-github)

维护者每个发布周期只选择少量外部案例处理，明确正式支持的引擎版本、输入规模和订单类型。社区适配器需要贡献者维护；没有责任人和契约测试的适配器标记实验性。核心 GA 必须交付 CLI/SDK、搜索、证据核验与导出，以及支持范围内的升级、恢复和维护能力；HTTP API、MCP 与 UI 仅在需求明确并通过各自验收后发布，不拖延已达到全部核心门槛的 1.0。正式发布前应有迁移说明、错误恢复指引、公开样例的干净环境验证，以及对已知限制的稳定解释。

## 8. 商业发现单独开展

当出现稳定重复使用后，邀请用户评估有明确范围的付费试点。访谈要区分实际使用者、技术批准者和预算持有人：谁从结果中受益，谁承担集成和算力成本，谁能批准购买，以及他们今天已经为什么付费。

第一轮商业测试优先考虑本地集成与有验收条件的研究审查服务。交付物可以是适配器、可重现案例、团队报告规范和培训；不出售“保证收益”“证明没有风险”或无法独立检查的总评分。

团队内网版、托管批量计算和报告协作各自是一项待验证需求。至少两个独立团队提出相同问题并愿意承担费用后，才评估产品化；先计算部署、更新、安全隔离、数据治理和支持成本。单个定制客户的需求不能自动写进开源核心路线图。

商业测试至少记录：请求来源、已有替代、使用频率、必要能力、试点价格与交付成本、成交/拒绝理由、续用行为。价格目前未定，不以访谈中随口给出的预算作为已验证市场规模。

## 9. 决策节奏与收缩门槛

以下周期是验证工作安排，不是承诺上线日期；以实际交付和可用参与者为准。一个维护者加 AI 仍需要为招募、领域判断、版本维护和支持预留时间。

| 检查点 | 应当拿到的证据 | 缺少证据时的动作 |
| --- | --- | --- |
| S1–S2 的早期问题访谈 | 既定 Sprint 预算内完成 3–4 次痛点访谈，记录近期案例与当前替代方法 | 缩小用户画像、调整招募，按预算置换工程范围 |
| 至 S6 的累计访谈批次 | 累计 8–12 次有效访谈、问题记录、至少 3 个案例承诺 | 缩小用户画像，调整招募渠道；不继续增加平台模块 |
| 首条可运行闭环后的陪同试点批次 | 3–5 个外部案例、基线对照、有效见证和完整失败记录 | 若工具无额外价值，收缩成核验/报告插件；若输入难，优先降低接入成本 |
| S12–S13 阶段前启动激活观察；Beta 前验收 | 至少 3 位外部激活，其中至少 2 位有限帮助下完成自有研究 | 处理安装、错误诊断、输入契约；未达门保留 alpha，不以新增可视化掩盖接入问题 |
| GA 前且每位参与者满 30 天观察窗口 | 至少 2 位外部用户在各自窗口内自发完成第二项不同研究，并记录研究决定 | 回访为什么不再用；未达门保留 RC，没有复用前暂停托管与大范围营销 |
| 可用版本后 6–8 周 | 持续采用、可承担支持成本，或明确收缩结论 | 保留最有价值的最小工具；停止没有证据支持的产品扩张 |

发生无效反例被当作有效、核验产物无法重放或报告错误暗示“未发现即通过”时，立即停止发布相关结论，修复并更正受影响产物。找不到反例、用户拒绝采用、简单基线更好，均应进入决策记录。

每月复盘维护负担：以支持、依赖升级与案例排错的合计时间为分子，以当月总可用净工程容量为分母。连续两个月各自超过 25% 时，冻结新适配器、减少支持组合并改善自助诊断。每 Sprint 的 15h 日常质量预算还承担测试、评审和文档，不是该阈值的分母，也不是可全部投入支持的额度。若一个用户需要长期专用分支，视为服务项目或拒绝，不拖入通用核心。

## 10. 证据记录与公开口径

采用统一记录而不覆盖历史。建议在项目实际进入执行时维护以下产物：

- 访谈登记：日期、匿名角色、近期案例、当前做法、原话与解释、参与同意、后续承诺。
- 假设登记：假设 ID、验证办法、预设门槛、实际结果、偏离、决策及证据链接。
- 试点卡：研究主张、输入授权范围、约束来源、基线、预算、维护者帮助、结论与研究行动。
- 采用登记：激活日期、是否满观察窗口、复用案例、团队交接与退出原因。
- 发布案例清单：数据来源、许可、版本、可复现状态、已知限制和更正记录。
