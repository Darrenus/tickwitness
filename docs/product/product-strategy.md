# TickWitness 产品策略

状态：开发前产品方案，尚未验证产品需求。最后更新：2026-10-25。TickWitness 是面向量化研究的研究证据平台；项目入口见 [README](../../README.md)。

本文中的“已有证据”仅指列出的外部资料或未来可检查的项目产物；“假设”指待验证判断；“目标”是决策门槛，不代表已经达到。当前没有用户访谈、真实采用、性能评测或付费验证结果。

## 1. 产品决策

为已经使用回放引擎的量化研究者提供一个本地研究审查工具：把一项回测结论写成明确主张，记录它依赖的数据与执行假设，在允许的范围内搜索能使主张不成立的反例，并交付另一位研究者可以独立复现的证据包。

首先解决的工作是：“这个研究结论依赖哪些目前无法观察的条件？我应该继续研究、补采数据，还是停止投入？”首批交付形态是 CLI、Python SDK 和可离线阅读的报告；通过适配器调用现成回放引擎。成熟产品应能够持续安装、升级、迁移、复现和排错，而不只是一段演示。

核心投资集中于受约束反例搜索、结论可识别性判断及证据链。采集、回放和统计分析服务于这项工作，不同时重建通用量化平台。核心 GA 必需 CLI/SDK、搜索与证据闭环，以及支持范围内的恢复、升级和维护能力；HTTP API、MCP 与 UI 在有需求且独立验收后可选发布，不阻塞核心 1.0。Agent 仅负责提出实验和解释已核验的结果。

已有技术依据：HftBacktest 的官方文档说明，市场数据回放不能改变历史市场，也不模拟自身订单的市场冲击；缺少 Market-By-Order 数据时，需要用模型估计队列位置。这使“哪些结论由数据决定，哪些由模型决定”成为一个具体工程问题。[HftBacktest Order Fill](https://hftbacktest.readthedocs.io/en/latest/order_fill.html)

| --- | --- | --- | --- | --- |

以上角色均是招募假设。第一版不以大型机构采购、交易终端用户或只想获得买卖信号的人群作为设计中心。

用户的代码和行情可能不能公开，因此“本地完成一次有用审查”必须独立于账号注册、数据上传和云服务。公开反馈可以只包含合成复现、脱敏配置或摘要；这不降低内部复现对原始输入的要求。

## 3. 核心流程与产品语义

### 3.1 定义可审查的主张

研究者先提交策略版本、数据清单、回放引擎版本、基线结果、指标和判断阈值。例如：“在给定样本与允许的执行假设集合内，该策略的费用后收益始终为正。”这不同于声称策略将来一定赚钱。

主张必须注明样本区间、交易品种、订单规模、费用、延迟、队列模型和评估指标。阈值在搜索前固定；改主张、改范围或改预算均产生新版本。无法运行基线、缺少关键输入或适配器不支持所需语义时，先给出可操作的输入诊断。

### 3.2 区分事实、未知量与压力情景

| 类型 | 示例 | 产品允许作出的解释 |
| --- | --- | --- |
| 已记录事实 | 原始消息、接收时间、序列号、已观测成交 | 作为约束，不为了得到更差结果随意改写 |
| 与观测相容的未知量 | 聚合订单簿中撤单发生于队列前方还是后方；有依据的时钟偏差区间 | 搜索符合约束的多种补全或执行解释；相反结论的有效见证说明当前证据不足以确定方向 |
| 额外压力情景 | 人为增加 10 毫秒延迟，或删掉一段原本完整的消息 | 说明策略对额外退化的敏感性；不得冒充真实历史或与全部原始观测相容的重建 |

序列缺口不等于可以恢复真实历史。无法从快照、协议和其他可用证据确定中间路径时，保留未知状态，限制可审查范围，或请求补充数据。约束本身需要来源；研究者主观选择的范围必须明确标注。

### 3.3 搜索、收缩、核验和交接

1. 验证证据清单并复现基线，输出环境与模型差异。
2. 冻结主张、允许变化的变量、约束、搜索预算和扰动距离。
3. 在预算内调用适配器执行搜索，记录成功、失败、取消和拒绝的尝试。
4. 找到反例后，按预先定义的距离和收缩规则减少变化，形成容易解释的见证。
5. 使用独立的约束校验与重放步骤核验见证；核验失败的候选不能成为反例。
6. 导出报告与证据包，由另一环境或评审者复现，然后决定补采数据、修正模型、继续研究或停止。

“最小反例”默认只指在已执行收缩步骤下无法继续缩小，报告必须给出距离、已尝试的邻域和预算。未经穷举或可检查的优化证明，不能称为全局最小。

报告应直接回答：审查了什么、改变了什么、为什么允许改变、结果如何变化、哪些部分仍不知道、怎样重现。建议行动必须引用对应证据，不把指标下降自动解释成真实交易失败。

### 3.4 结论标签

下表规定面向用户的语义，具体机器枚举由领域模型统一定义。

| 标签语义 | 必要条件 | 不代表什么 |
| --- | --- | --- |
| 已发现并核验反例 | 一个满足声明约束的见证使主张不成立，且独立核验通过 | 不代表所有执行情形均亏损，也不代表策略没有其他用途 |
| 本预算内未发现反例 | 搜索正常结束，报告实际覆盖、预算、算法和未探索部分 | 不代表不存在反例，不等于安全认证或统计显著 |
| 声明在指定模型内不可识别 `NOT_IDENTIFIABLE_WITHIN_MODEL` | 至少两个满足同一观测约束、均完成独立核验的见证，使同一声明分别成立和不成立 | 只覆盖所列证据与模型，不得把压力情景的相反结果或主观模型选择冒充该结论 |
| 证据不足 `INSUFFICIENT_EVIDENCE` | 关键变量缺少有依据的约束，或输入、执行覆盖、样本或证明链不足以支持判断 | 不等于已证明不可识别；缺少约束本身不是两个相反有效见证 |
| 输入或范围不支持审查 | 关键证据缺失、协议不满足、范围不受支持 | 不等同于策略失败 |
| 运行未完成 | 超出资源、取消、引擎错误或核验失败 | 不得默认为审查通过 |

有限集合上的穷举结论只能覆盖该集合；连续范围的边界证明需要额外方法及证明产物，不属于首版承诺。模拟假设内的结果、样本不确定性和未来市场泛化分别陈述，不能用一个“可信度分数”混合。

## 4. 范围与非目标

首版保留一个维护者能够承担的支持面：一个主回放引擎、一个明确的行情输入契约、少量公开或合成数据样本、一个经核验的搜索流程，以及 CLI/SDK 的稳定交接。只支持经过验证的市场和订单类型；不支持的情况明确拒绝。

首批主要考虑“小订单对市场影响可忽略”的研究。大订单市场冲击、隐藏流动性和交易所内部优先级不会因为多跑几个情景就变得可知。NautilusTrader 同样将历史订单簿视为不可修改的记录，并提供不同的流动性消耗及成交模型设定；适配器必须携带这些语义，而不是只搬运 PnL 数字。[NautilusTrader Fill Prices and Matching](https://nautilustrader.io/docs/nightly/concepts/backtesting/fill-prices-and-matching/)

首版不承诺以下能力：实盘下单、自动发现可盈利 alpha、完整向量化与事件驱动双引擎、自建全市场 tick 数据服务、全语言静态分析、任意代码的形式化正确性证明、恶意宿主环境中的防篡改、机构合规认证、多租户托管服务。数据授权、交易连接和账户管理不进入核心领域。

HTTP API、MCP 与报告 UI 是可选交付入口，安排在 CLI 与证据契约可用、且用户需求明确以后；各自未通过验收时不发布其能力，也不阻塞满足全部核心门槛的 1.0。Agent 不计算最终裁定，不修改核验产物，不自行扩大假设范围。可复现运行与防止任意权限进程作弊是两个不同要求；前者是本产品目标，后者需要独立的隔离与威胁模型。

## 5. 竞品关系与待验证差异

以下是截至 2026-10-25 的公开资料审查，不是完整市场调查。外部项目可能更新；采用前应固定版本并重新核对许可证、接口和限制。

| 既有方向与来源 | 已有能力 | 本项目拟验证的差异 |
| --- | --- | --- |
| [Qlib / RD-Agent](https://github.com/microsoft/qlib) | 量化研究工作流、模型及回测，并接入研究自动化 | 给既有研究追加“主张—允许假设—反例见证—独立核验”流程，而不复制因子与模型平台 |
| [HftBacktest](https://hftbacktest.readthedocs.io/en/latest/order_fill.html) | 市场数据回放、成交和队列模型 | 编排多个声明过的模型假设，解释结论为何翻转；引擎是依赖及潜在集成伙伴 |
| [Freqtrade lookahead-analysis](https://www.freqtrade.io/en/stable/lookahead-analysis/) | 通过重复回测比较指标和信号，检测特定前视偏差 | 审查执行与观测未知量中的结论依赖，不能把“多跑几次回测”本身称为创新 |
| [leakguard-mcp](https://github.com/doazvjettu/leakguard-mcp) | MCP 入口的启发式静态泄漏规则 | 用执行见证验证声明范围内的反例；静态扫描可作辅助，不能替代核验 |
| [Qanat](https://github.com/fidetolabs/qanat) | 财报数据、历史时点指标和 MCP 查询 | 不竞争通用数据查询入口，专注研究结论与不可观测条件的关系 |
| [asof-research](https://github.com/oscar-chw/agentic-quant-research/blob/main/platform/README.md) | 冻结假设、封闭测试窗口、重算证据的研究 harness | 把重点放在与观测相容的执行未知量及反例收缩；其公开 README 也说明真实模型研究循环尚未完成 |

尚待验证的独特价值是“以更低集成成本，为真实评审发现手工参数扫描容易漏掉的有效反例，并帮助用户采取行动”。我们没有证据证明该组合全球首创，也没有证据证明它优于现成脚本。若等预算参数扫描加一页报告即可满足用户，应缩成工具或上游插件。

## 6. 产品假设与衡量方式

所有数值均为首轮验证目标，记录真实基线后再调整；不用于 README 的已实现成绩。详细实验见 [用户发现与采用计划](discovery-and-adoption.md)。

| 假设 | 测量办法 | 初始目标 / 决策门槛 |
| --- | --- | --- |
| H1：审查痛点频繁且有成本 | 最近一次真实案例访谈，记录时间、损失的工作和现有解决法 | S1–S2 在既定预算内完成 3–4 次早期痛点访谈，至 S6 累计 8–12 次；累计样本中至少 5 人能提供近 90 天具体案例，至少 3 人愿意投入自己的案例 |
| H2：证据输出比原始参数表更可行动 | 同预算对照：现有手工/网格扫描与平台报告；记录评审者判断及所需时间 | 至少 3 个外部案例中，2 个产生被研究者接受的修正、补采或停止决定；不能只统计指标变差 |
| H3：接入不需要迁移研究栈 | 记录从干净环境到用户自有案例的主动操作时间与维护者协助时间 | Beta 门槛：至少 3 位外部研究者激活，其中至少 2 位在文档和一次有限排错帮助下完成自有研究；未达则保留 alpha |
| H4：结果可以交接 | 由未参与原运行的人或隔离环境验证证据包 | 所有公开宣称为已核验的反例均通过独立约束检查和见证重放；偏差须解释，不能删除失败记录 |
| H5：存在持续使用而非演示兴趣 | 跟踪外部用户在首例后 30 天是否审查新研究 | GA 门槛：至少 2 位外部用户已满 30 天观察窗口，且在各自窗口内自发完成第二个不同研究；未达则保留 RC，不用缩短观察期替代 |

核心产品指标是“外部研究被独立复现且触发可记录研究决定的数量”，以案例为单位去重。辅助指标包括首个有效结果所需时间、核验成功率、用户可独立处理的错误比例，以及每个案例的维护者支持时间。

搜索性能必须与固定预算的网格/随机扫描比较：核验有效见证数、找到首个见证的时间、固定预算下发现率、约束违反候选率和收缩结果。只有算法对照支持时才扩大自动搜索投入。报告运行耗时、内存、磁盘和失败率时同时写明数据规模、硬件、引擎版本及预算。

守护指标包括：把未完成或无反例误写为通过的次数、不可复现见证数、无效约束被接受数、干净对照被误报数、报告被读者误解为收益保证的次数。这些问题优先于新增特性。Stars、下载量和访问量仅作触达诊断，不作为产品价值证明。

## 7. 成熟与可持续性的产品要求

每个正式支持的组合均有明确版本范围、最小样例、故障解释、证据包格式版本和升级说明。旧报告可继续阅读；迁移不得覆盖旧证据。依赖升级先过基准案例及适配器一致性检查，再进入支持矩阵。

本地流程默认不上传策略、数据或环境信息；可选诊断输出先供用户检查。没有遥测也必须可用。报告中需要展示的实现细节限于用户做判断所需的版本、假设和证据来源，其余放到可展开诊断或机器清单。

维护策略按能力扩展：一个维护者负责发布与技术决策，AI 用于实现、检查和文档草稿；AI 输出仍须经过确定性验证和人工领域评审。先保持一个主适配器，第二个引擎只有在真实需求和贡献维护能力明确后进入正式支持。通过模板收集问题，合并重复案例；不承诺全天候支持。

产品完成标准不仅是代码通过：还包括外部用户能安装和使用、无维护者陪同能复现公开样例、升级有记录、常见失败可恢复、反例的适用边界清楚，以及维护成本持续可承担。可信本地 CLI/SDK 的激活观察应在 S12–S13 阶段前启动，不等待可选 API、MCP 或 UI。Beta 需至少 3 位外部用户激活，其中至少 2 位有限协助完成；GA 需至少 2 位已满 30 天观察期的外部用户在窗口内自发完成第二项研究。采用门与技术、正确性和运维门共同验收；Beta 未达保留 alpha，GA 未达保留 RC。

## 8. 开源生态与商业化候选

项目软件已选择 Apache-2.0 许可，具体条款见仓库 [LICENSE](../../LICENSE)。开源核心的目标是保持完整的本地闭环：主张与证据格式、约束校验、基础搜索与收缩、见证核验、CLI/SDK、官方样例及主适配器。证据格式和核验器可以独立使用，避免用户离开服务后无法读取或验证研究资产。上述产品能力仍是待实现计划；Apache-2.0 不代替依赖与数据各自的权利记录，不把免费可下载等同于可再分发。

生态顺序是先与一个引擎集成，再沉淀可复现案例，随后支持社区适配器。社区适配器与正式支持组合分开列示；接受贡献要有责任人、契约测试和兼容说明，避免维护者承担所有上游变化。GitHub Issues 用于可复现缺陷，Discussions 用于研究问题与集成讨论。[GitHub 官方协作工具说明](https://docs.github.com/en/get-started/using-github/communicating-on-github)

商业方向均为待验证选项，不是确定路线：

| 候选 | 潜在付费理由 | 开始前必须获得的证据 |
| --- | --- | --- |
| 集成与研究审查服务 | 把现有研究接入并形成可交接证据 | 有外部团队愿意为有范围、有验收的试点支付费用 |
| 团队内网版本及支持 | 私有数据、统一版本、报告交接和故障响应 | 至少两个团队独立提出相同需求，且需求不是一次性定制 |
| 托管计算和报告协作 | 批量运行、共享计算、审批及长期产物管理 | 本地用户持续使用，并明确愿意将对应数据或任务托管；隔离和运维成本可以覆盖 |

不先建多租户账号、计费、云采集和大规模存储。托管属于后续交付上下文，不进入首版核心模型。若无付费需求，可保持小而可靠的开源工具；商业化失败不自动等于技术无用，反之演示受欢迎也不证明商业成立。

## 9. 停止、收缩和继续条件

在每个验证批次结束时记录实际样本、偏离原因和决策，不通过不断移动门槛维持“进展”。

| 触发条件 | 默认动作 |
| --- | --- |
| 8–12 次有效访谈仍少于 3 个愿意提供的真实案例 | 暂停扩大工程范围，改为定位更具体角色；若两轮仍无需求，保留可复用核验工具并停止平台化 |
| 连续 3 个真实案例中，现有脚本在相近时间和预算下已满足全部审查需求 | 收缩成报告/核验插件；先验证工作流价值，不继续投入复杂搜索 |
| 所需未知量无法给出有依据的约束，结果主要由主观范围决定 | 将该案例归入“假设敏感性”而非可识别性结论；优先补采或缩小可支持任务 |
| 反例有效性或复现出现严重错误 | 停止新增搜索能力和“可靠”宣传，先修复、补对照并更正受影响报告 |
| 连续两个月，支持、依赖升级与案例排错合计超过各月总可用净工程容量的 25% | 冻结新适配器，缩小支持矩阵，优先稳定版本与文档；分母不是每 Sprint 的 15h 日常质量预算 |
| 首批可用版本后 6–8 周，已激活用户没有新的研究复用 | 回访原因并调整流程；在持续使用出现前不建设托管和商业基础设施 |
| 有重复使用、可核验价值和可承担维护成本 | 扩大案例库或增加一个高需求能力，避免同时扩资产、引擎和用户界面 |

这些是预先写下的产品决策规则；任何调整都保留旧版本及调整依据。产品方向靠外部研究任务中的证据继续，而不是靠“革命性”定位继续。
